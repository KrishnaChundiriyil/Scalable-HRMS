# Contract with Person 1's real Employee & Auth Service

The leave module has **no bundled fake Employee Service** and does **not** ship any fake employee records. Person 1 owns employee identities and the authoritative directory.

## Identity contract (agree before Person 1 starts)
- Person 1's authentication endpoint issues signed **HS256 JWTs** for development with the shared secret supplied *outside Git* as `HRMS_JWT_SECRET_BASE64`.
- JWT `sub` = stable `employeeId` such as `EMP001`.
- JWT claim `roles`: array with any of `EMPLOYEE`, `MANAGER`, `HR`, `ADMIN`.
- JWT contains `exp` (expiration) and `iat`.
- Every service validates the signature and expiry itself; do not trust browser-supplied employee IDs.
- For a more production-like identity provider, later migrate to **RS256 or OIDC JWKS** with issuer/audience checks; this is a documented future security hardening task.

## Employee directory contract

`GET /api/employees/{employeeId}` at `EMPLOYEE_SERVICE_URL` (default `http://localhost:8082`).

Header: `Authorization: Bearer <JWT>` forwarded from the requester.

Success `200` JSON:
```json
{"employeeId":"EMP001","name":"Example Employee","department":"Engineering","active":true}
```

`404` if employee unknown, `401`/`403` for unauthorized access, `503` when service unavailable.

Leave service uses this **only for read-only employee-profile display**. It caches a successful response in Redis for 5 minutes. A circuit-breaker fallback may return the last cached profile with `stale: true`, but never treats stale data as authority for approvals, account creation, or role assignment.

## Shared data conventions
- `employeeId` is the same immutable ID in every module.
- Person 2 stores its own leave ledger in `hrms_leave` MongoDB; it does not write into Person 1's employee collection.
- Person 3 may later consume attendance / approved-leave events for payroll. This version exposes the leave API as the canonical source; Kafka event integration belongs in the cross-team integration phase.

## Dataset guidance
The **employee search/autocomplete dataset belongs to Person 1's Employee Service** (or a team-owned synthetic sample employee dataset imported into it). It is **not required to run Person 2's leave algorithm**. Leave records reference `employeeId` generated by Person 1, not a second independent employee list. No real employee personal data should be committed.
